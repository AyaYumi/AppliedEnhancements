# BigInteger 规划路径检查（1.21.1 / 1.0.9）

2026-09-17 实测日志：终极精华订单 `10000000000000000`，6 个节点、0 个边界，AELIS 在 `child_request_overflow` 后回退到原生递归，直到玩家取消。这证明前一版只补拓扑路径并不足够。

| 路径 | 检查结果与本轮处理 | 剩余限制 |
| --- | --- | --- |
| 数量输入、取消返回、可选 DE 菜单 | 精确十进制输入、双向菜单同步；普通 long 订单仍可使用 DE 菜单 | 超 long 最终订单已贯通；不要求安装 DE；最多256位输入预算 |
| 普通拓扑 | 需求、分支求和、样板次数保持 BigInteger；补精确缺失账本 | 库存、发射器和原生边界仍是 long |
| 事务路径：消耗材料、可复用催化剂 | 递归需求、乘法、除法改为 BigInteger；保留输入顺序、实际库存扣除和催化剂借还；字节估计保留精确分数并在汇总后取整 | 有限耐久工具的实际分配仍用 long，不拿截断后的次数分配工具 |
| 替代输入 | 大整数需求逐模板扣除 long 库存，保留模板顺序与余物验证 | 非消耗型替代或动态语义仍按原规则拒绝/交给受限边界 |
| 有序多候选 | 编译候选内部进入同一大整数事务执行；合并缺失投影防溢出 | 候选分配和原生候选仍是 long，不宣称任意规模支持 |
| 全局/局部循环 | 检查求解、种子、输入与执行次数转换；补缺失元数据 | 求解器虽用 BigInteger，执行调度仍要求 long；超限不能截断为可执行循环 |
| 数量反馈配方 | 检查事务进入点、需求和库存验证的 long 边界 | 反馈批次模型仍用 long；超限报告不支持 |
| 回退到原生 | 溢出、原生工作量超限、超过 100 万的根订单回退均停止并提示 | 保护只在大整数规划开启时生效；小规模兼容回退保留 |
| 子计划合并 | long 样板计数饱和时保留投影标记；精确样板次数、产量与缺失量只合并一次 | 精确元数据必须随计划保留 |
| 计划提交 | 不再因超 long 强制 simulation 或在菜单/提交入口统一预判执行能力；交由所选 CPU 返回提交结果 | 原生 long 接口仍是饱和投影；CPU 扩展需要读取精确任务与材料元数据，允许提交不等于已验证完整执行 |
| 摘要、同步、显示 | 待合成、缺失、本单库存供应量及计划字节数同步精确值；关闭增强材料显示也保留防溢出摘要；沿用 E 以上单位；协议 7 | 网络载荷预算仍有限；原生存储接口及 CPU 兼容字段仍为 long |

验证包括实际事务执行器的五级 ×4 链、`10^16` / `10^18` 订单、库存扣除、余量归还、真实缺料分支、关闭开关，以及元数据复制与网络预算测试。开发服集成检查加载真实 AE2 状态和 Mixin，执行同形配方链，验证单个自返催化剂的借还、精确缺失/产量/样板次数、子状态合并、投影标记、摘要与网络往返。

这些检查不等同于在用户整合包中完成实际 Mystical Agriculture 配方复测，也不意味着所有第三方动态配方都获得任意精度执行能力。

## AE2: Crafting Tree 兼容回归

随后用户整合包日志确认 `10^18` 终极精华订单已成功完成 AELIS 规划，但发送 `ae2:craft_confirm_plan` 时，ae2ct 1.1.1 的 `RecipeHelper jobs` 为 null。大整数路径的提前返回跳过了 ae2ct 的尾部初始化；普通路径替换整个摘要也可能丢失其他模组元数据。

修复：普通路径原地更新条目，保留摘要实例及附加元数据；大整数路径通过可选反射桥调用 ae2ct 自己的工厂和设置接口补齐合成树，不引入硬依赖。集成检查使用用户整合包中的 ae2ct 1.1.1，修复前复现同一空指针，修复后覆盖普通、`10^16`、`10^18` 请求的完整 AE2 确认数据包编码/解码，并检查合成树目标与配方条数；额外覆盖关闭增强材料显示和 API 包装计划。

## 合成树数量、完整浮窗与无限元件

AE2CT 节点构造另有 `input.amount * times` 的 long 溢出。开启 BigInteger 规划时，使用可选兼容桥以 BigInteger 构建节点需求、整除进位与缺失分配，保留 AE2CT 原有布局。原字段只作非负 long 投影，节点文字（包括截图）读取精确元数据，浮窗显示分组的完整数字。树仍沿用 AE2CT 每个产物首个配方的展示模型，不等同于复杂多候选/循环计划的完整执行轨迹；循环展开有边界。确认表浮窗不再走缩写或 DECIMAL128 舍入，流体单位也保留完整小数。

无限支持受 `storage.infinite.enable_listing_limit_bypass` 控制，仅识别明确元件标记。在服务器线程快照当前可访问的无限物品，规划线程不访问世界；实际网络取出通过当前挂载包装器模拟检查后供给，不消耗元件。规划子分支分别记录无限消耗，成功合并时转移，失败分支不污染父状态；最终目标的 ignore 语义仍保留。常规拓扑与事务路径直接满足任意精度无限材料需求，普通 long 规划也可反复提取。复杂循环/原生边界仍受上表限制，不能据此宣称所有算法都支持任意精度。

无限材料不参与确认菜单的有限库存预留；未标记的 Long.MAX_VALUE 存储仍是有限库存。超 long 的材料暂存预算保留精确值与投影标记，不再强制仅预览；真实缺料仍保留 simulation。整合包开启此选项；项目默认仍为 false，保留已有配置兼容。

验证覆盖真实 AE2 状态和 Mixin、AE2CT 1.1.1 的递归大数节点与缺料筛选、客户端节点格式化/浮窗、无限元件反复取出、子分支合并与回滚、禁止提取、卸载、开关关闭、有限 Long.MAX_VALUE、外部列表叠加，以及两个确认菜单同时预留。

## 确认页“可用数量”完整大整数

用户复测发现“可用数量”仍显示 9,223,372,036,854,775,807。原因是无限消耗账本在模拟状态中保留精确值，但 `usedItems` 投影到 long 后，计划、同步包与确认菜单没有携带对应的精确字段。

补齐 `bigIntegerStoredAmounts`：从已提交子分支的精确库存供应账本传到计划，API 复制/包装计划保留，协议 6 同步到菜单，确认表的 FromStorage 行与合成树读取精确值。三种精确数量共用网络字节预算。保留“可用数量”原行，不显示 ∞，不增加“本单使用”行；此处沿用 AE2 确认页含义，即本单由已有库存供应的数量，不是整个网络的库存容量。

9,000,000,000,000,000,000 的五级 ×4 订单，其底层材料可用数量为 9,216,000,000,000,000,000,000：列表 9.2Z，悬停完整数字。回归检查覆盖该订单、子状态合并/丢弃、计划复制、服务端编码/客户端解码与 FromStorage 单行/混合缺失和待合成行，防止只修数字格式却漏同步字段。

## CPU 自行决定提交结果

移除确认菜单的统一 long 计划验证、提交入口的统一拦截，以及投影标记导致的强制 simulation 和仅预览提示。精确样板次数随状态、子分支合并、计划与 API 复制保留；不新增 CPU 能力注册或白名单。原生 CPU 选择逻辑、实际缺料状态和既有循环执行协议不变。

开发服检查使用真实 AE2 CraftingService、CraftingCPUCluster 和 Mixin：上述材料齐全订单进入离线 CPU，原样返回 CPU_OFFLINE；真实缺料订单仍返回 INCOMPLETE_PLAN。此检查证明提交路径已放行，不证明整合包中的 CPU 能完成超 long 的实际执行。原生 long 投影仍存在，执行扩展需消费精确任务及库存供应元数据。

## 标题的合成存储字节数

标题曾从原生 long `usedBytes` 读取值，固定在 9.2EB；同时拓扑/事务路径曾在计费前截断请求量、样板次数和催化剂逻辑用量。现在沿用原有 AE2 计费公式，以大整数分数累计字节估计，子分支成功时只合并一次，整份计划结束后向上取整。流体以及自定义每字节数量的除法不提前舍入；原生 double 贡献按其传入值保留，不宣称恢复第三方在调用前已损失的精度。

`bigIntegerBytes` 经计划、API 复制、协议 7 和确认菜单传到标题，复用 Z/Y/B…Att 扩展单位并附加字节 B。外部计划未提供精确字段时沿用原字节数。不改 CPU 选择/提交、不新增执行检查，原生 long 兼容字段仍可饱和。

检查覆盖五级 ×4 催化剂链的独立字节公式、拓扑路径、long 操作数乘法、嵌套分支合并/丢弃、流体小数、元数据复制和网络往返，以及客户端标题读取精确字段而非 9.2EB 投影。
